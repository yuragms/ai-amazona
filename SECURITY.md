# Security audit and practices

Краткий чеклист аудита и рекомендации по безопасности.

## Проведённый аудит

### Аутентификация и авторизация
- **NextAuth (JWT)**: пароли не хранятся в открытом виде, используется bcrypt; роль в JWT/session.
- **Middleware**: защита маршрутов `/admin` (только ADMIN) и `/dashboard` (только авторизованные) реализована в `middleware.ts` — редирект на `/login` при отсутствии сессии.
- **Server actions**: все админские и пользовательские действия проверяют `auth()` и при необходимости `session.user.role === "ADMIN"`.

### API и вебхуки
- **Stripe webhook**: проверяется подпись `stripe-signature` через `constructEvent`; без валидной подписи запрос отклоняется.
- **Секреты**: ключи Stripe, Resend, Uploadthing, AUTH_SECRET берутся из `process.env`, не захардкожены.
- **test-email**: отключён в production (`NODE_ENV === "production"` → 404).

### Ввод и XSS
- **Отчёты (Print/PDF)**: данные, подставляемые в `document.write` в export-reports, экранируются через `escapeHtml` (period, categoryName, customerName, status).
- **Prisma**: запросы параметризованы, риск SQL-инъекций минимален.
- **Опасные паттерны**: в коде не используются `dangerouslySetInnerHTML`, `eval`, неконтролируемый `innerHTML` для пользовательского ввода.

### Зависимости
- Регулярно проверяйте уязвимости: `npm audit`.
- Критичные обновления применяйте по возможности: `npm audit fix` (перед этим убедитесь, что тесты проходят).

### Рекомендации перед production
1. Задать надёжный `AUTH_SECRET` (например, `npx auth secret`).
2. Использовать HTTPS; при необходимости настроить заголовки безопасности (CSP, HSTS) в next.config или на уровне прокси.
3. Ограничить частоту запросов к критичным эндпоинтам (например, forgot-password, login) через rate limiting (прокси/CDN или отдельный middleware).
4. Не коммитить `.env*` с реальными секретами; использовать переменные окружения в CI/CD и на хостинге.
